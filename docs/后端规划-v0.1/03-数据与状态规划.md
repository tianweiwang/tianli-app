# 03 数据与状态规划

## 1. 数据设计范围

已核对 [06-数据模型](../06-数据模型.md)：52 张一期业务表、2 张优惠券预留表。本稿在此基础上补齐实现所需的交易、方案明细、权限与执行记录。这里是逻辑模型，字段类型、完整索引和迁移 SQL 在工程阶段评审后生成。

| 业务域 | 继承的主要表 | 实现时补齐的内容 |
| --- | --- | --- |
| 组织与资格 | store、technician、insurance、transfer、leave、admin_user、duty_roster | 门店渠道能力和证据、技师隶属生效历史、角色与数据范围 |
| 身份与归属 | user、verification、consent、restriction、promoter、binding/history | AppID 下的身份唯一性、同意版本、首单资格的并发判定 |
| 项目与资源 | service_item、store_service、slot_price_rule、shift、slot_occupancy | 价格快照、完整时间区间、占用版本和释放原因 |
| 预约与履约 | orders、order_event、reassignment、reschedule、termination | 派单轮、提案版本、服务事实、业务状态与资金状态分离 |
| 售后与安全 | aftersale_case、review、appeal、penalty、sos_event/notification | 每笔支付的申请额、协商方案版本、并列的结算阻断 |
| 交易与结算 | refund、order_split、adjustment、profit_sharing/return、recovery_ledger | 支付交易、退款占额、退款方案、渠道通知和日账单差异 |
| 佣金与开票 | promoter_commission、withdrawal、authorization、tech_commission/adjust、invoice_request | 提现分配明细、余额变动、合并开票关联、红冲凭证 |

表名使用现有全名，表中部分名称为简写。`orders.parent_order_id` 延续加时子单关系；每个子单拥有自己的支付、退款和渠道分账记录。

## 2. 建议补充的持久记录

这些是实现建议，最终物理表数量按 DDL 评审确定，不以“凑齐某个表数”为验收标准。

| 记录 | 关键字段/关系 | 必须保证的约束 |
| --- | --- | --- |
| payment_transaction | order_id、out_trade_no、transaction_id、sub_mchid、amount_fen、status、paid_at、close_status | 商户单号唯一；已付金额与门店收款方固定；保存每笔真实支付 T0 |
| dispatch_round | order_id、round_no、trigger_type/id、started_at、deadline_at、confirmed_at、status | order_id+round_no 唯一；同一触发事件只开一次轮；截止创建后固定 |
| aftersale_payment_item | case_id、payment_id、requested_fen | 每笔申请额明确关联支付；不以 JSON 金额数组代替可锁定明细 |
| refund_plan / refund_plan_item | case_id、version、total_fen、payment_id、amount_fen、accepted_at | 已确认方案不可改；明细合计等于总额；执行只引用该版本 |
| settlement_blocker | order_id、source_type/id、opened_at、closed_at | 售后、安全、客服、退款可同时阻断；只关闭自身来源 |
| promoter_account / account_entry | promoter_id、available/frozen/debt_fen、version；来源交易和余额变动 | 余额更新与流水同事务；来源业务号去重；更正以反向记录处理 |
| withdrawal_allocation | withdrawal_id、commission_id、amount_fen | 同一笔佣金可分批提现时，累计分配不能超过可用额 |
| channel_notification | channel、event_id、transaction_no、payload_digest、received_at、processed_at | 通知去重；验签后持久化；原始敏感内容按最小保留范围处理 |
| outbox_event / durable_job / job_attempt | aggregate_id/version、event_key、due_at、lease_until、attempt、result | 业务提交和待执行事件同事务；重试可追溯、重启可恢复 |
| idempotency_record | actor_id、route、key、request_hash、result_ref | 同键同请求复用；同键异请求拒绝 |
| role / role_permission / admin_role_assignment | role_id、action、admin_id、store_scope、valid_until | 操作和数据范围共同生效；停用可撤销 |
| audit_log / file_asset | actor、resource、action、reason、request_id；文件用途、归属和访问级别 | 敏感查看、变更和下载留痕；附件下载重新鉴权 |
| reconciliation_bill / reconciliation_difference | channel、sub_mchid、business_date、file_hash；差异类型/金额/处理人 | 同渠道账单幂等导入，差异有来源和处理结果 |
| invoice_payment_item | invoice_request_id、payment_id、invoiced_fen、red_flushed_fen | 合并主单/加时可追溯，累计开票不超净实付 |

`reassignment`、`reschedule` 继续分别记录业务变更，补充 proposed_at、expires_at、version、状态、原值与拟改值、关联临时占用。仅发起提议时不覆写 orders 的当前有效技师、时间和地址。

## 3. 订单采用独立状态维度

原需求的“已退款、已结算、售后中”等文案可以由多个维度组合生成。后端以事实与独立状态保存，避免退款或安全结案覆盖服务完成事实。

| 维度 | 建议值 | 说明 |
| --- | --- | --- |
| booking_status | WAIT_PAYMENT、WAIT_CONFIRM、CONFIRMED、IN_PROGRESS、COMPLETED、CANCELLED、CLOSED | 预约主进度 |
| fulfilment facts | departed_at、arrived_at、started_at、completed_at、end_type | 仅有真实事件才记录；保留事实来源和操作人 |
| payment_status | UNPAID、PAID | 每笔支付单独记录，订单展示聚合结果 |
| refund_status | NONE、PROCESSING、PARTIAL、FULL、NEEDS_ACTION | 失败待垫付与处理中分笔记录，成功金额以渠道结果为准 |
| settlement_status | WAITING、BLOCKED、PROCESSING、SETTLED、NEEDS_ACTION | 与服务进度和退款独立 |
| support cases | 售后/中止核实/争议各自状态 | 有未解争议时投影为客服或售后处理中 |
| safety events | 待接报、升级、处理中、结案、无人响应 | 独立于订单，支持多个事件及通知 |
| proposal_status | 待确认、接受、拒绝、过期、失效 | 原约和新提案分开保存 |

V3 显示实际出发、到达等履约事件；V4 对应预约进度。显示映射不能改写完成时间、收款门店、退款结果或授权范围。后台详情同时展示这些维度，客服可追溯判断依据。

## 4. 已确认规则的落地约束

| 规则 | 保存与校验方式 |
| --- | --- |
| 首次支付后固定派单期限 | 首轮 deadline=min(首次支付+30分钟，预约开始−60分钟)；切候选和重试不更新 |
| 确认变更新开一轮 | 新约生效与新轮创建同事务；新轮 deadline=min(确认时间+30分钟，新开始−60分钟) |
| 门店派单直接确认 | 通过权限、资源、期限检查后直接 CONFIRMED，记录提成规则版本和通知事件 |
| 指定改派需要用户确认 | 未完成轮受当前轮截止限制；已确认订单的新指定改派，在接受时生效并由门店完成分配 |
| 紧急请假只重派可重派订单 | 检查本人、完整时间重叠、已确认且尚未开始相关履约；已出发/开始/完成事实阻止自动回退 |
| 正常完成须满时长 | 服务端校验实际服务时长≥项目+有效已付加时；提前结束单独记录原因且不自动退款 |
| 求助结案保持最新事实 | 关闭该安全事件；重算其他阻断和显示状态；completed_at、取消和资金终态保持 |
| 协商退款按申请额拆分 | 分为整数分，最大余数补齐；固定主单优先及支付顺序；确认后锁定方案 |
| 提现失败/撤销仍计次数 | 创建申请、锁佣金和每日次数校验同事务；按创建日计数，幂等重复不新建 |
| 价格和资金快照固定 | 肩颈默认198/228元由规则给出；分成、收款方与价格从提交快照取，改价不改旧单 |

派单开始前60分钟的截止已过，且该轮尚未分配成功时，立即进入取消退款流程。任何迟到命令都先检查服务端时间和最新轮号。

## 5. 资源占用事务

占用区间包括前后缓冲，建议统一为半开区间 `[start_at, end_at)`；两个区间的重叠条件是 `old.start < new.end AND old.end > new.start`。

1. 根据命令找出相关技师、订单、支付和账户。涉及多位技师时按 ID 排序锁定，再按固定顺序锁订单等记录；锁后重读实际关联和版本，变化时重试整个命令。
2. 校验最新门店状态、项目资格、有效保单、排班、请假、覆盖和期限。
3. 使用锁定读取检查所有有效占用，写入或切换资源；预约、改约、改派、加时使用同一路径。
4. 改约接受时，将新占用生效、原占用释放、订单变更、次数及新派单轮一次提交。失败则保持原约。
5. 本事务同时写业务事件和待执行任务。提交后发送通知和调用渠道。

普通请假和停业审批也必须走资源校验；它们不能绕过占用锁。数据库死锁或乐观版本冲突只允许有限次数重试，并保留同一幂等键。

支付占用超时先调用关单并查询结果。渠道结果未知时保持处理中，不能仅因本地倒计时到点就释放。晚到支付按真实 paid_at 和当前资源重新判断：仍可合法恢复则恢复；已冲突或业务已不允许履约则原笔全额退款。加时支付回调还需复验主单状态和资源，不能在主单已结束后增加有效时长。

## 6. 金额与退款占额

每笔支付的尚可退金额 = 实付 − 已成功退款 − 已确认但尚未完成的退款占额。生成/接受方案时锁定相关支付，重查剩余额度，再固定分笔金额和交易号。

退款失败需要人工处理或重试时保留该方案占额；只有明确撤销未执行方案才能释放。成功时在一个事务内将占额转为已退款，写调整事件。两个案件或两位操作员同时退款，也只能分配剩余额度。

例如主单申请98元、加时申请49元，协商100元，固定为主单66.67元、加时33.33元。主单成功、加时失败时，重试仍只执行33.33元；已成功主单不再退款，整体显示部分执行成功/仍待处理。

主单与加时分别保存支付 T0、渠道交易、分账截止和退款额度。预约最远范围仍锚定首次主单支付；改变派单轮不会改变资金期限。强制分账前对未终态退款先查渠道并核对占额，避免把结果未知的金额当成可分资金。

## 7. 索引与一致性重点

- 业务单号、渠道交易号、幂等键、通知事件号设符合业务范围的唯一约束。
- 待办用 `(store_id, status, deadline_at)` 等与实际查询匹配的组合索引；财务列表按子商户、状态和时间过滤。
- 占用先锁技师，再按 technician_id、状态、时间区间查找；唯一“开始时间”不能防住区间重叠。
- 有效客户归属在锁定用户后更新，并限制同一用户仅一条当前有效归属；历史记录追加保存。
- 提现锁账户及对应佣金，创建日次数、金额、分配和账户变动一起提交。
- 金额用整数分、比例用万分比；每次结算记录规则版本和舍入结果，退款调整保留原记录。
- 凭证与个人信息字段加密/分级存储；密码使用适当的单向密码哈希。日志和导出不输出密钥、身份证明文或完整支付报文。

## 8. 需要定下的一处业务歧义

docs/03 要求下单固定分成快照；docs/04 又以“第一笔完成且未全退的主订单”认定首单。用户同时下两单、完成顺序相反，或首单全退时，首单佣金金额何时固定尚未明确。

建议下单保存首单/复购两档规则版本，首次符合条件的完成事务锁定首单资格，再确定适用档；全退回退和后续已结算订单如何调整需一起确认。这会细化既有快照规则，当前只列为决策项，不擅自更改业务基线。
