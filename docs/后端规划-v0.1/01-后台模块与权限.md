# 01 后台模块与权限

## 1. 使用方式

门店、集团共用一个登录入口。账号登录后由服务端返回角色、权限和可管理门店；导航随权限生成。门店工作台进入本店，集团工作台可筛选门店。后台角色不增加为小程序角色。

列表、详情、待办与报表使用统一结构：列表支持业务状态、时间、门店、人员与异常筛选；详情展示预约事实、资金、处理记录；待办显示截止时间和责任人；导出使用当前账号的数据范围。业务量和交易金额均来自实际数据，初始页面提供空状态。

## 4. 预约详情作为共用核心页面

统一使用“摘要 + 允许操作 + 分区详情 + 时间线”结构：

- 摘要：订单号、服务门店、项目及价格快照、时段、技师、预约状态、付款/退款/结算摘要。
- 分配：当前轮、触发原因、固定截止、候选、原技师、新技师、用户决定；改约展示原时段和拟改时段。
- 履约：实际开始和完成时间、正常/提前结束/中止原因；V3 显示对应履约事件，V4 按预约状态投影显示。
- 资金：主单与加时支付逐笔展开，实付、已退、处理中占额、尚可退、分成、回退、佣金和提成。
- 客服、安全、售后：各事件的状态、时限、证据、处理人、结论和结算阻断。
- 发票与日志：净可开票额、红冲结果、规则版本、变更和渠道任务时间线。

敏感资料按字段授权；完整联系方式、真实地点及附件的查看必须有业务理由、授权和访问日志。完成后技师端隐藏详细地点，留存期限依原需求待定规则执行。

## 5. 权限建议

原需求包含六类后台账号；集团运营作为建议的独立角色补充，避免日常运营使用全权限账号。

| 角色 | 主要权限 | 数据范围 |
| --- | --- | --- |
| 集团管理员 | 账号、授权、全局管理配置；业务财务操作按另授角色判断 | 全集团授权范围 |
| 集团运营（建议补充） | 项目、门店、技师、分销、规则草稿与业务报表 | 全集团授权范围 |
| 集团财务 | 分账、回退、追偿、提现、账单、财务规则和开票汇总 | 全集团财务范围，个人信息最小化 |
| 集团客服 | 售后裁决、特批、中止核实、投诉、限制和申诉 | 与处理案件相关的订单和客户 |
| 安全负责人 | 求助、升级、值班和复盘 | 与安全处置相关的数据 |
| 店长 | 本店预约、派单、排班、售后、门店规则和推广 | 当前授权门店 |
| 门店财务 | 本店对账、提成标记、发票、退款财务待办 | 当前授权门店 |

同一账号可具备多个角色。权限由“动作 + 资源范围 + 字段范围”组成；店长是否同时拥有财务角色由实际授权决定。

服务端从会话推导可访问门店。列表、详情、操作、附件和导出统一检查资源归属；后台提交的 store_id 只能缩小筛选范围。账号停用、技师调店、离职、门店关闭后刷新或撤销相关授权。集团裁决跨店访问也要检查案件权限。

财务重试仅针对已有交易；账单差异、规则变更、线下核销均保留原因和凭证。金额阈值、双人审批等额外机制如要采用，需作为新业务规则确认。

## 6. 页面设计顺序与通用状态

第一批：后台框架、登录及权限、门店/集团工作台、预约列表/详情、派单池、候选技师、改派/改约确认、售后列表/详情、排班与请假。第二批：对账/分账/回退/追偿/提成/开票。第三批：组织生命周期、项目规则、推广、客服安全、权限和看板剩余细节。

各批仅代表设计顺序；一期模块均须在正式上线前完成。

必须覆盖：加载、空数据、网络重试、无权限、已被别人处理、操作过期、校验失败、部分执行成功、渠道处理中、失败待处理、导出生成中及过期。动作先显示影响范围、原值/新值、金额及原因；完成后刷新服务端事实。批量审批或派单逐条返回成功与失败，不能显示误导性的全部成功。
