## 3. P1：应优先修正

### OLD-01 我的预约没有用户隔离，能取消别人的预约【B、F、S】

- **触发**：切换李四→我的预约→打开陈女士 `BK202607302001`→确认取消。
- **实际**：列表包含其他顾客及另一门店的预约；陈女士预约被取消，相关容量被释放，当前身份仍是李四。
- **根因**：[Bookings-tMJbsXsj.js:1](../../design/reference-demos/franchise-demo/assets/Bookings-tMJbsXsj.js:1) 的 `visibleBookings` 仅按状态过滤；[BookingDetail-mfb9_rv4.js:1](../../design/reference-demos/franchise-demo/assets/BookingDetail-mfb9_rv4.js:1) 仅按 ID 查详情。主包 `Lj/eB`（偏移 984417/984726）取消时也不校验用户。
- **修正规则**：列表、详情和写动作全部校验订单所有者；代预约联系人不等于订单权限所有者。
- **验收**：李四看不到陈女士预约；即使进入其链接，查看与取消均拒绝，陈女士的订单和容量不变。

### OLD-02 接受推广会串到第一位已绑定顾客【B、F、S】

- **触发**：已有 U1 的有效推广绑定，再由 U2 接受另一条推广。
- **实际**：`activeCustomerId` 变为 U1，返回 U1 的绑定，没有为 U2 建立正确关系。
- **根因**：主包 `oB`（988773）使用 `distributionBindings.find(...status === "active")`，未限定顾客；随后 `HC`（987975）切换当前顾客。
- **影响**：推广行为可以把顾客身份、会员信息和后续订单归错人。第一轮为函数级；第二轮已在浏览器先接受好友甲、再接受好友乙，个人中心仍显示好友甲，见 [第二轮截图](verification/round2/customer-second-friend-is-first.png)。
- **修正规则/验收**：来源处理只影响当前用户的推广上下文，不改变登录身份；两位用户先后接受同一或不同推广时各自独立。

### OLD-03 库存既不限制购买数量，也不随成交扣减【F、S】

- **触发**：库存 1，购买 99 件；或者连续两次各买 1 件。
- **实际**：两种场景均可生成已支付订单，库存始终为 1。
- **根因**：主包 `J3`（980476）只检查 `stock > 0`，不比较数量、不预占或扣减；[cart-BTpTOt_f.js:1](../../design/reference-demos/franchise-demo/assets/cart-BTpTOt_f.js:1) 也未约束累计数量。
- **修正规则**：提交锁库存、付款转已售、未付关闭释放；下单校验具体 SKU 和数量。
- **验收**：最后一件只能被一笔有效订单占用；付款、关闭、重试均只处理一次。

### OLD-04 新商品单只能走到已支付，缺少履约和退款链路【B、S】

- **触发**：购买 398 元修复液，会员实际模拟支付 338.30 元，生成 `ORD202607301006`。
- **实际**：详情停在“已支付/品牌仓库正在准备商品”；无取消、收货、退款入口。用户、门店和集团订单页均主要是查看，已配送/已完成/已退款来自种子样例，无法从新订单连贯走到。
- **位置**：[OrderDetail-C0W-_zGn.js:1](../../design/reference-demos/franchise-demo/assets/OrderDetail-C0W-_zGn.js:1)、`Orders-CH0fEzP3.js`、`Orders-CEFg1gSf.js`、`Orders-C99mUv8O.js`；主包 `J3` 创建 `paid`。
- **修正规则**：补模拟出库、运单、收货、取消、退货验收、部分退款、失败重试与售后结案。没有真实物流并不妨碍 Demo 模拟这些业务事件。

### OLD-05 商品结算缺少明确的业务条件和逆向资金约束【F、S；闭环缺项】

- **触发**：商品刚支付，在集团分账详情依次开始分账、确认完成。
- **实际**：商品仍 `paid`，分账已经 `completed`；100 元合成订单可产生 80 元门店可提现额。
- **根因**：主包 `nB`（986050）和 [ProfitSharingDetail-1wPFrAlj.js:1](../../design/reference-demos/franchise-demo/assets/ProfitSharingDetail-1wPFrAlj.js:1) 只检查分账状态转换，不检查履约、售后或退款。
- **判断边界**：没有旧完整 PRD，不能仅凭未收货就断言违反旧结算政策。已证实的是：支付后可立刻分账，未定义其业务条件，且后续履约退款缺失、回退与提现脱节。此项按本次要求的闭环缺口列入优先处理。
- **整合建议/验收**：明确收货、售后等待期和无阻断等商品可结算条件，并由动作本身校验；在采用该建议后，未满足条件不能通过手动按钮跳到可付款。

### OLD-06 门店收入已回退为零，旧提现仍能继续付出【F、S】

- **确定缺陷**：门店先提交 80 元提现，随后对应已结算收入全部回退为 0，原提现仍能经两次审批到 `completed`；没有对应冻结、垫付或债务记录来解释这笔支出。
- **关联观察**：分账完成→回退完成后，个人佣金仍是 `settled`，仍能提交 10 元提现。但渠道回退不必然等于商品退款或取消个人佣金权益，不能仅据此断定个人佣金应全额扣回。需要记录回退原因、业务退款和应调整金额的关联。
- **根因**：主包 `nB` 与 `lB`（989871）、`uB`（990744）之间没有处理回退导致的资金约束变化；审批只推进提现状态。仅把可见负余额钳为 0 无法解释债务。
- **修正规则**：根据真实业务退款/调整确定权益，再处理未付冲减、付款中核查、已付追回；渠道回退独立记账。付款审批检查锁定明细及调整，不能只推进状态。
- **验收**：收入回退后不可新增无依据付款；已有付款中的金额最终进入冲销或追偿，用户退款不等待追偿成功。

### OLD-07 创建预约即送积分，取消后还能保留并支付服务【F、S】

- **修正规则**：明确奖励事件，建议合格服务完成后幂等发放；取消/退款反向调整。营销积分与储值赠分的用途、过期和欠分处理需定清。

### OLD-12 100 期补贴缺少合法周期推进与控制【F、S】

- 集团会员页 `currentPeriodKey` 写死 `2026-W31`，执行一次后仍只能请求同一期，无法连续演示下一期。
- 主包 `Z3`（979158）只按任意字符串去重，不核对业务时钟、合法周期和本计划应发期。
- **函数级结果**：同键重复被阻止；同一业务时刻传入 100 个不同键可发完 100 期、共 5100 元。页面没有任意键输入，**不能称为浏览器可一键刷完补贴**。
- **修正规则/验收**：按明确周期计算应发期，计划+期号唯一；只允许已到期未发的一期，失败重试不算新期。Demo 提供推进合法周期的控制并展示下一期。

- **修正规则/验收**：把原计划、预约、任务、报告串联；完成新报告时关闭原计划，再生成下期。取消或未完成保持明确待安排状态。

## 5. 业务政策与整合冲突，不与程序缺陷混为一谈

| 问题 | 当前证据 | 整合前需要明确 |
| --- | --- | --- |
| 集团销售与旧分账模型不一致 | 支付页写集团收款，订单却按门店收入+集团抽成；服务结算还含代理 | 采用已确认的集团销售+门店商品佣金；旧比例作废或另立约定 |
| 商品归因与预约归属混用 | 页面当前门店、长期绑定、全局当前客户相互影响 | 按用户已确认方案独立保存商品来源与订单快照 |
| 储值发行与跨主体消费 | 本金可扣、收益可模拟，但充值收款方和跨店清算未明确 | 谁发行/收款/承担退款；能在哪些店和商品使用 |
| 会员开卡折扣前提 | 510 开卡不增加本金，服务 6.6 折仅能选本金支付；无本金时无法完成该折扣结算 | 开卡即折扣还是另需储值；能否微信支付，文案一致 |
| 赠送权益、券和套餐 | 有 benefitGrants 展示，无完整锁定、核销、取消返还与退款 | 适用范围、次数、有效期、叠加、退款后处理 |
| 积分共用一个余额 | 预约奖励和储值赠分均可用于同一服务消费 | 分清种类及用途、发放/回收/过期、欠分处理 |
| 补贴的资格、资金来源和出口 | 累计消费达标生成计划，余额增加；缺少消费退款调整及余额使用/提现 | 周期、资金承担、重复达标、退卡退款后计划与已发补贴怎么处理 |
| 区域代理比例与停用 | `Aj` 按绑定代理固定 15%，不读档案比例或状态；当前 UI 仅展示 | 是否纳入商城、从谁收益中出、比例快照、停用和追偿；不冒称已在界面改比例复现 |
| 核销的业务含义 | 核销后可会员结算、启动检测 | 核销表示到场还是完成；与预约先付款流程如何衔接 |
| V4 实际服务地点和扣费事实 | 仍列正式接入待定，但影响是否可服务和取消费用 | 采集/确认/覆盖校验时点，事实记录、用户告知和争议入口 |
| 预约首单并发与全退 | 原后端规划已列未决问题 | 首单资格认定、规则快照、后续差额补结或追回 |

以上在 [02-整合业务闭环](02-整合业务闭环.md) 给出建议处理链路，未确认的权益不会写成既定规则。

## 6. 模块覆盖与未验证部分

| 模块 | 本轮覆盖 | 边界 |
| --- | --- | --- |
| 商品/购物车/支付/订单 | 组件与核心函数；浏览器完成一笔新支付 | 未接真实支付和物流；库存并发为函数边界，非真实数据库并发压测 |
| 资金/分账/提现/推广 | 状态函数、7 个隔离场景及种子一致性 | 未执行真实转账和跨设备持久化 |
| 预约/核销 | 列表、详情、创建、取消、核销；浏览器越权取消 | 非真实接口鉴权或微信扫码验收 |
| 会员/积分/补贴/代理 | 相关页面、领域函数、正反例与政策缺口 | 函数测试含合成客户和周期，不等于当前 UI 所有入口均可触发 |
| 检测/设备/复评 | 开始、回传、授权、发布、复评、到期；浏览器第二检测 | TL1002/无影像/过期分支为函数验证；设备页主要只读 |
| 直播 | upcoming→live→ended 及 live 动作门槛、关联入口静态核对 | 未发现该状态链的可证实跳转缺陷；无真实直播平台验收 |
| 门店/代理/进件/报表 | 展示、组织及资金规则关联；报表金额核对 | 非真实进件、合同或支付机构资质核验；设备维护/代理签约完整流程未实现 |
| 与当前项目整合 | V0.3/V0.4、后台规划及用户本轮决定对照 | 未修改预约、商城或后台原型实现 |

已验证的有效保护也应保留：取消预约后核销会被拒绝；会员结算检查门店、已核销状态和余额；重复结算不重复扣款。旧 store.commit 先克隆、成功后才提交，不能将草稿中途抛错的修改误报为真实持久扣款。

## 7. 修正顺序

1. 先定整合规则和首批范围，统一账户、订单所有者、收款与佣金主体。
2. 修 OLD-01～07，完成商品正反向流程与资源/资金约束。
3. 如果检测纳入同版，修 OLD-08/09/13/14；会员纳入则同时修积分、金额、补贴和权益逆向链。
4. 统一种子金额、消费记录和报表口径，移除无法走完的功能入口或明确未纳入范围。
5. 按 [场景验收](03-场景验收与决策.md) 从新建业务开始跨角色验证；通过后再称相应范围的 Demo 闭环完成。
