# 04 演示流程与当前项目对齐

日期：2026-10-02。用户追加要求：**整个 Demo 的演示流程和交互逻辑，都要与当前项目对齐。** 本文定义下一版原型的基准与连续脚本；当前仍为先审查、先梳理阶段，未修改现有原型。

## 1. 对齐基准

优先级为：用户已确认决定 → 预约版 v0.4 增补 → V0.3 业务基线和后台规划 → 本次新增建议。未确定的费用、权益或范围按 [03 决策清单](03-场景验收与决策.md) 标注，不能由旧页面或种子数字自动决定。

- 预约以 `docs/预约版-v0.4/需求说明.md` 为准，保留已确认的派单、改约、请假、加时、退款和安全规则。
- 后台职责以 `docs/后端规划-v0.1/01-后台模块与权限.md` 为准，维持门店/集团两端。
- 商品采用已确认的集团统一销售发货、门店推广获佣、本次有效推广来源下单锁定。
- 旧商城提供功能参考和问题证据；旧到店核销、旧分账、个人商品佣金和补贴不能自动成为整合版规则。
- 预约页面按预约表达，不丢失实际服务责任、地点确认和取消费用依据，不混入另一套到店服务承诺。

## 2. 当前三套原型并没有共享业务

| 产物 | 已有联动 | 当前存储及边界 |
| --- | --- | --- |
| `design/prototype-v4`，4184 | 用户/技师/店长在一个 iframe 中切换、处理一笔预约 | `runtime.js`：sessionStorage 的 `tianli-v4-reservation-demo`；单笔 state、固定样例 orderNo |
| `design/admin-prototype-v1`，4186 | 门店/集团后台共用本套订单数组 | `model.js`：localStorage 的 `tianli-admin-v1`；独立订单、门店和技师 ID |
| `design/reference-demos/franchise-demo`，4187 | 旧消费者/门店/品牌角色共用旧状态 | localStorage 的 `tianli.franchise-demo.v1`；已发现跨顾客隔离错误 |

三个端口还是不同的浏览器 origin，没有共享数据或同步桥。把三个链接放在导航里、显示相似顾客和金额，都不能证明前后端已贯通。

下一版需要**一个统一演示入口、一份业务记录、五个视图**：用户、技师、店长小程序、门店后台、集团后台。仍对应现有三类小程序身份和两个后台。

每笔订单在各视图使用同一 ID、金额快照、事实和事件记录。切角色只改查看与操作权限，不能加载另一笔样例。刷新恢复同一份记录；重置/切换情景必须由演示者明确触发。

V4 的 `xingfu/lin` 与后台的 `s1/t1` 等标识需要统一；旧锦江/滨江门店不能仅改名字就视作当前幸福里门店。演示数据按当前项目重新生成，真实历史数据迁移另行处理。

还需统一多笔订单、用户和金额：V4 以单笔 state 为主，再次预约会重建当前记录；后台是独立订单数组。整合后必须保存历史、给新订单生成唯一编号，并以 customerId 关联用户。V4 的主要金额按元、后台按分，统一账本应采用整数分。V4 的当前时间偏移与后台的固定推进时间也要换成同一业务时钟。

## 3. 页面与动作映射

实际 V4 底部导航（`components.js`）：用户“首页/预约/我的”，技师“预约/排班/收入/我的”，店长“看板/安排/排班/待办”。整合建议只在用户导航加入商城；技师工作入口保留，店长增加推广及佣金摘要。旧商城没有技师端，不能替代当前 V4。

以下是当前已有页面/后台路径的对应关系，代表各原型内部已有交互，**跨原型同单联动仍待建设**：

| 业务 | V4 当前页面/动作 | 当前网页后台 |
| --- | --- | --- |
| 项目、门店、技师、时段 | u-stores / u-service / u-tech-picker / u-slots | #/hq/stores、#/hq/catalog、#/hq/technicians、#/store/schedule |
| 确认和支付 | u-confirm → pay → u-payment-success | 尚无用户新建/支付流入后台的连接 |
| 接单和派单 | accept-appointment / reject-appointment / store-assign | #/store/orders、#/hq/orders 的订单详情 |
| 改派和改约 | u-reassign / u-store-reschedule / u-reschedule | 订单详情中的提案及用户决定 |
| 开始、完成和加时 | start-appointment / finish-appointment / pay-extension | 订单事实、时间线和分笔支付；目前主要为本套样例 |
| 请假 | t-leave → s-leave-review → approve-leave | #/store/schedule |
| 售后和退款 | u-aftersale-apply / u-aftersale-confirm / u-refund-processing | #/store/aftersales、#/hq/aftersales |
| 求助、发票 | request-care / close-care / u-invoice | #/store/safety、#/hq/safety、#/store/invoices |

后台目前的“待分配”与 V4 的 `waiting + confirmationPhase` 不能直接一对一替换：用户的待确认包含技师确认阶段及门店待派子状态。草稿和已提交待支付也应分开保存。客服、安全、退款各自保留独立事件及资金结果，不能仅替换主状态文案。

| 旧页面或交互 | 对齐后的行为 | 复用边界 |
| --- | --- | --- |
| 首页直接预约到店 | 当前预约：区域/门店/项目/具体技师/时段→确认→付款 | 以 V4 主线为基础，取消旧到店核销主链 |
| 服务与商品共用分类 | 服务进入预约，商品进入商城 | 推荐可一起展示，提交、支付、资源各走各的流程 |
| 商城必须挂某门店 | 集团销售，门店只是有效推荐来源，允许无来源购物 | 不能由预约选店或地理位置暗改商品佣金 |
| 全局购物车、固定地址 | 每用户购物车与地址，SKU/数量/配送/来源校验 | 必须新增；旧固定地址不算可用地址管理 |
| 支付时直接建已付单 | 先生成待支付单、占库存，再模拟支付结果 | 新增失败、超时和晚到结果 |
| 商品付款后只能查看 | 集团发货→用户收货→售后退款→佣金结算 | 新增完整商品正向与逆向流程 |
| 门店收入＋集团抽成＋代理 | 集团商品收入、推广门店佣金、退款调整 | 重建公式和样例，不能复制旧金额 |
| 预约创建即送积分 | 按明确的合格业务事件发放，取消/退款可回收 | 当前预约不因此默认新增营销权益 |
| 核销后扣会员余额 | 与当前预约确认/开始/完成事实衔接 | 会员资产未定前不保留相冲突的第二套结算 |
| 个人和门店共用提现流程 | 预约个人佣金与商品门店对账付款分开 | 商品门店结算新增，不能套用个人零钱提现 |
| 会员/补贴/代理/检测/直播 | 按已审查结果和确定范围启用完整链路 | 未纳入时说明范围，不展示能扣钱却无退出的入口 |

## 4. 主演示：同一用户的一笔预约和一笔商品

使用一套标为虚构的用户、组织、库存和业务时间，金额读取规则与流水。A 为商品推广店，B 为本次服务店，不混同客户原归属。

| 步骤 | 当前视图与动作 | 各端必须同步的结果 |
| --- | --- | --- |
| 1 | 用户从 A 店商品分享进入 | 建立本用户商品来源；不改预约归属、不切换顾客身份 |
| 2 | 用户选规格、加购物车 | 只改本人购物车；不占预约时段、不预扣库存 |
| 3 | 用户进入预约，选择 B 店、项目、具体技师和时段 | 形成预约草稿，保留商品购物车；按 D05 确认地点与覆盖 |
| 4 | 用户提交预约并模拟付款 | 技师待确认、B 店待办、集团列表出现同一预约；B 店收款，派单截止固定 |
| 5 | 技师确认，或 B 店成功派单 | 用户已确认；门店派单不再等技师二次确认 |
| 6 | 技师开始、服务满时长后完成 | 用户进行中→已完成；B 店生成提成，进入服务售后期，资金状态独立 |
| 7 | 用户回到购物车，确认地址、商品、运费、A 店来源并提交 | 集团新增商品待支付单、占库存；不能把 B 店变成商品推广店 |
| 8 | 用户模拟商品支付成功 | 集团待发货，A 店出现脱敏推广订单及预估佣金；预约及技师收入不变 |
| 9 | 集团仓储出库并登记运单 | 用户待收货，A 店仅看推广进度；库存与出库一致，店长无发货权 |
| 10 | 用户收货，推进时间至满足结算条件 | 无售后阻断时佣金转可结算；不能手动绕过业务条件 |
| 11 | 集团出账，A 店核对，集团财务模拟付款 | 待核对→付款中→已付；失败可重试且不重复付款 |
| 12 | 用户查看两类订单、发票和客服 | 服务由 B 店开票，商品由集团开票；收款、退款、净额和历史同单可追溯 |

中途不得加载另一张“已完成样例”来替代实际操作。演示设置用于模拟外部支付/物流/设备结果和推进时钟；能由产品角色完成的决定，在主演示中须切到该角色的实际页面处理。

## 5. 必走的七条连续异常分支

### B1 预约派单超时

用户付款→技师拒绝/超时→B 店看剩余期限→多次选择候选→到期取消、退款处理中→模拟失败→资金待办→原笔查询重试成功。各端同一预约号，切候选不延长截止。

### B2 指定改派与改约

店长提出新安排→用户看到原安排及待确认提案→用户接受/拒绝→门店同步。拒绝指定改派按规则退款，拒绝门店改约保持原约。后台“模拟用户接受”可保留为单页测试工具，整合主演示应走用户页面。

### B3 请假、正在服务和求助

技师提交完整起止时间请假→店长看影响、批准→只允许重派的单入池；正在服务不回退。用户求助→店长/集团接报→技师实际完成→客服结案→保留完成和资金结果，其他争议未解仍阻断结算。

### B4 商品取消与部分退货

未发货取消→库存释放→原路退款。另一商品单出库→收货→申请退一件→集团受理→用户填退货单→仓储验收→退款→剩余商品/佣金继续。验收驳回后演示申诉和货物返还去向。

### B5 佣金已付后退款

沿主线完成 A 店佣金付款→商品部分退款→集团先退用户→A 店出现应追回→下期商品佣金抵扣或回款→追偿结清。不能扣 B 店预约款、技师提成或改预约归属。

### B6 身份与数据隔离

甲有预约/商品/购物车→切乙→只见乙的数据→访问甲链接被拒。再切 A/B 店与集团验证数据范围和动作。推广处理不能把乙切成甲。

### B7 会员与检测（决定纳入后）

会员从开卡/充值开始，经权益使用到取消/退款/清算；补贴至少两个合法周期及消费退款调整。检测完成两条任务、另一店任务、拒绝影像、异常回传和复评关闭，不能仅第一条样例成功。

## 6. 同一业务必须保持的一致性

| 数据 | 统一原则 |
| --- | --- |
| 身份 | 用户 ID、登录角色、服务对象、联系人分开；切角色不改订单所有者 |
| 门店与技师 | 一份组织和资格记录，小程序与后台同一 ID 指同一对象 |
| 订单 | 预约/商品分类型；同单在对应授权视图可找到，列表详情一致 |
| 时间 | 一个演示业务时钟，所有截止和升级共用，不能各页重新起算 |
| 状态 | 展示可按角色投影，事实与允许动作取同一规则；资金不覆盖履约 |
| 金额 | 价格、数量、优惠、实付、退款和佣金取同一快照与流水，统一分币算法 |
| 资源 | 时段与库存分别管理，取消/超时/重试只释放一次 |
| 待办 | 责任人、期限和失败接手人明确；结案只关闭相应来源待办 |
| 通知 | 通知失败不回滚业务；订单仍可查，待办可重试通知 |
| 日志 | 记录操作人、时间、对象、结果；金额调整追加记录 |

## 7. 原型改造的完成标准

1. 纳入范围涉及的重大决策已明确，演示参数有标签和版本。
2. 一套种子数据支持主线和异常分支，金额能从流水解释。
3. 小程序与两后台实际共享同一笔业务，不能继续维护同名样例。
4. 旧问题有修复或明确移出范围记录，现有预约关键规则回归验证。
5. [52 条验收场景](03-场景验收与决策.md) 记录实际结果，并明确未纳入扩展模块。

本轮完成对齐基准和演示脚本设计；原型改造、共享状态和跨端联动验证尚未执行。
