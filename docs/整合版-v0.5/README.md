## 本轮任务

- 审查旧商城自身的业务逻辑，包括交易、库存、预约、会员、补贴、分成、提现、检测和直播。
- 将已确认的集团商城模式与现有预约业务整合，写明每个流程的责任人、状态、金额、异常出口和验证条件。
- 保留现有已确认规则；新建议、待决策和仅用于演示的数字分别标注。
- 审查阶段保留旧产物源码，记录隔离证据；用户随后授权独立建设 `design/integrated-v5`，统一五视图、商品交易与预约联动。
- 第一阶段使用明确标注的演示参数；真实接入、完整 52 条验收及未纳入模块继续保留在任务与范围记录中。

## 已确认的整合决策

1. 商品由集团统一销售发货，门店推广获佣。
2. 商品佣金按本次有效商品推广来源确定，下单锁定。自然进入且无推广记录时归集团、不产生门店佣金。
3. 当前仍是 Demo 阶段，但业务流程必须能够从发起走到明确结果，包含失败和逆向处理。
4. 审查覆盖旧商城全部主要业务模块；会员、套餐、补贴、代理等扩展模块未纳入本次第一阶段，其经营规则和后续范围仍待确认。
5. 整套演示流程和交互逻辑以当前项目为准；新整合版五视图读取同一笔本地业务，旧商城保留为功能参考及审查证据。
6. 预约以原 V4 操作为主，保留分步选择、告知与确认。商城增加在既有预约入口旁，统一数据不得替换或简化已认可的操作逻辑。

## 使用边界

- **已确认**：用户直接确认的业务方向。
- **承继**：来自现有需求的规则；原文仍作为预约基线。
- **建议**：为形成完整流程而提出，不能当作已经批准的合同、费率或资金权益。
- **待决策**：会改变费用、权益、范围或业务责任，必须在对应功能作为已定稿演示前解决。
- **演示参数**：用于验算和流程演示，可配置、有版本；不代表已经核验的渠道规则或商品售后政策。

本稿不把本地模拟支付、纯函数测试、截图或静态代码审查称为真实支付、硬件接入、微信审核或生产验收。
